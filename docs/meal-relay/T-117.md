# T-117 提供者頁 MR-P06：申請、食物點、上架、庫存去向（前端）

> 合約 [11-meal-relay.md](../system/11-meal-relay.md) v2.2（§2、§3 `meal_food`、M1、M5、M14、M19、§7、§8、V4、V21）｜issue #58

一般市民在這頁申請成為提供者並看審核狀態；審核通過的提供者選或新增食物點、上架食物，在「我的庫存」看每批食物的剩餘、派出中、已送達與無人認領提醒，可改份數與最晚食用時間、下架。
畫面只組合 `@/ui`、UI kit（[ui-kit.md](ui-kit.md)，MR-C07～C23）與 T-114 共用元件（[T-114.md](T-114.md)，MR-C01～C06），本頁專用元件用本工單的編號區間 MR-C35～C39。API 只在 `logic/supplier.ts` 經 `../data` 呼叫。

> **設計 v2（T-136）已改版畫面**：目前的畫面組成、元件與決策見 [§7 設計 v2](#7-設計-v2t-136issue-97)；§1～§5 是第一版的紀錄。

## 2. `logic/supplier.ts`

| 函數／常數 | 用途 |
|---|---|
| `qtyFloorOf(food)` | 已用掉的份數＝`dispatched_qty + delivered_qty`（M1、M14） |
| `editQtyMin(food)` | 改份數輸入框的下限：`max(1, qtyFloorOf)`（決策 2） |
| `qtyError(qty, min?, max?)` | 份數錯誤文字（沿用 kit 的 `qtyHint`）；空字串＝合法 |
| `toTaipeiIso(local)`、`toTaipeiLocal(time)`、`defaultExpiresLocal(now)` | `datetime-local` ↔ 含 `+08:00` 的 ISO；上架預設最晚食用時間＝現在＋3 小時 |
| `expiresError(local, now)` | 最晚食用時間不能早於現在（M14） |
| `emptyApplyForm`、`emptyPointForm`、`emptyFoodForm(now, point_id?)`、`editFormOf(food)` | 表單初始值；型別 `ApplyForm`、`PointForm`、`FoodForm`、`EditForm`、`FoodImage` |
| `buildSupplierApply`、`buildPointCreate`、`buildFoodCreate(form, now, image_id?)`、`buildFoodUpdate(food, form, now)` | 表單 → 請求內容（`{ ok, body }` 或 `{ ok: false, errors }`）；只送合約欄位，修改只送有改的欄位 |
| `errorText(e)` | §7：顯示後端回傳的中文訊息；不是 `MealApiError` 時用通用說法 |
| `editErrorOf(e)` | 修改失敗要標在哪個欄位：`QTY_BELOW_USED` → 份數（V21）；提到時間的 `VALIDATION_ERROR` → 最晚食用時間 |
| `canPublishWith(me, supplier)` | 只有 `role = supplier` 且 `status = approved` 能上架（V4） |
| `sortInventory(foods)`、`inventoryTotals(foods)` | 庫存排序（可派送的、新的在前）；四個統計（剩餘、派出中、已送達、還沒被派出的批數，M1、M5） |
| `pointMarkers(points, selectedId)`、`pointSubtitle(p)`、`pointSourceText(points)` | 食物點定位針、清單副標、SourceNote 文字 |
| `ORG_TYPE_LABEL`、`ORG_TYPES`、`POINT_KIND_LABEL`、`NAME_MAX`、`NOT_APPROVED_TEXT` | 中文與常數 |
| `useSupplierPage()` | 頁面狀態與動作：`load`、`refresh`（每 15 秒；審核中看是否通過、提供者更新庫存；用了舊資料時整個重讀）、`apply`、`selectPoint`、`addPoint`、`setImage`、`publish`、`openSheet(id, mode)`、`saveEdit`、`confirmClose`、`start`／`stop`；`view`、`canPublish`、`offline`、`staleAt`、`inventory`、`totals`、`markers`、`sourceText`… |
| 轉出型別 | `Allergen`、`Food`、`FoodCategory`、`Location`、`OrgType`、`Point`、`PointKind`、`Supplier`（ui/ 不能匯入 data/） |

## 3. 決策

| # | 決定 | 原因 |
|---|---|---|
| 1 | 上傳圖片前由邏輯層補上 `data:${mime};base64,` 前綴 | MR-C06 ImageInput emit 的 `data` 已去掉前綴，但 `uploadImage(dataUrl)` 與後端要完整 data URL；沒有改共用元件。T-114.md 寫「直接給 `uploadImage`」不正確，建議在 #50 更正 |
| 2 | 改份數輸入框的下限取 `max(1, 派出中＋已送達)` | 合約下限是 `dispatched_qty + delivered_qty`，還沒派出時會是 0；要歸零請用下架 |
| 3 | `datetime-local` 一律當台北時間，送出 `YYYY-MM-DDTHH:mm:00+08:00` | 合約 API 時間一律含 `+08:00`；不依手機時區 |
| 4 | 地圖只顯示食物點，選點用下方清單 | MR-C07 MapView 不能點定位針 |
| 5 | 只有 `approved` 的提供者才讀食物點與庫存；審核中顯示 `NOT_APPROVED_TEXT`，上架與新增食物點在送出前就擋；後端回 `SUPPLIER_NOT_APPROVED` 時顯示後端訊息並重新讀取 | 一般市民呼叫 `listPoints`／`listFoods` 會 `FORBIDDEN_ROLE`（V4） |
| 6 | 後端回 `QTY_BELOW_USED` 時面板不關、份數框變紅、顯示後端訊息，並重新讀取庫存讓下限更新 | V21：已派出份數可能在畫面打開後又變了 |
| 7 | 下架確認用 MR-C39 的 `close` 模式，不用 `window.confirm` | WebView 可能不顯示原生對話框 |
| 8 | SourceNote 用食物點的 `source` 欄位去重（去掉 `custom` 與「模擬」），沒有時用 T-115 登記的資料集名稱 | 畫面上的來源跟著實際資料走 |
| 9 | 輪詢時若有任何讀取用了裝置上的舊資料，就整個重讀（含 `getMe`、`getMySupplier`） | 只更新庫存的話，帳號仍是舊資料，連線恢復後送出鍵會一直停用 |

## 4. 範圍外發現（沒改）

- 後端 `meal_food.update_food` 只檢查擁有者，沒檢查提供者是否 `approved`（M14 寫「只有 approved 才能…修改、下架」）。
- MR-C11 QtyInput 在 `serverError` 時只顯示「份數不合法」，不顯示後端訊息；本頁在份數框下方另外顯示後端訊息與目前已用份數。

| `expiresText(expires_at, now)` | 「最晚 12:30 食用」；不是今天加「11/8」 |
| `defaultPointId(foods, points)` | 上架預設的食物點：最近一次上架用的、還在清單上的點 |
| `withoutAllergen(list, a)` | 過敏原晶片的 × |
| `ADDRESS_MAX`、`ApplyForm.address`、`PointForm.address` | 地址選填、最長 120 字，有填才送（去空白）；個人提供者不送（ADR-030） |
| `REJECTED_TEXT` | 未通過的說明（決策 v2-3） |

### 7.4 決策

| # | 決定 | 原因 |
|---|---|---|
| v2-1 | 三欄總計：**剩餘只算可派送（`open`）**；**派出中、已送達算全部批次**（含已結束） | 過期、下架的剩餘份數已經不會派出，算進去會誤導；已派出的份數下架後仍照常送達，已送達是提供者的成果，都該算。沿用 T-117 的 `inventoryTotals`（測試不變）；原本第 4 個統計「還沒被派出（批）」拿掉，改成每一列的 warn 晶片（M5） |
| v2-2 | 「全部送完」（`claimed`、剩餘 0、派出中 0）歸到已結束 | 合約 `FoodStatus` 沒有「全部送達」，但這批已經沒有事要做；還有派出中的 `claimed` 留在進行中，因為還能修改 |
| v2-3 | 未通過的「原因」顯示固定說明 `REJECTED_TEXT` | 合約 `Supplier` 沒有不通過原因的欄位；不改合約（工單限制），列為偏離，需要的話另開合約工單 |
| v2-4 | 下架改用 MR-C67 ConfirmDialog（danger），FoodEditSheet 只負責修改 | 設計 v2 §2；確認視窗先關、`confirm` 後才送出，所以要下架的 id（`closingId`）和視窗開關分開記 |
| v2-5 | 庫存列改用本頁的 MR-C85，不用 MR-C03 FoodCard | 設計圖的列是「照片、名稱、最晚 HH:MM 食用、剩餘・派出中・已送達、修改、下架」，按鈕至少 48px；MR-C03／C14 是共用元件，不能為了本頁改版面。照片仍用 MR-C55 FoodThumb（T-127），數字仍用 `useMotionNumber`（B2） |

| v2-7 | 上架仍是 T-127 的漸進式揭示：先拍照或「略過」，再展開其他欄位；StepIndicator 跟著走 | 和設計的「拍照 → 填寫資訊 → 上架」一致；照片選填（M19） |
| v2-8 | 上架預設選「最近一次上架用的食物點」 | 設計圖上已經有選好的食物點；提供者通常固定在同一個地方出餐。沒有上架紀錄時不選，送出鍵停用 |
| v2-9 | 申請表的地址由使用者自己填（選填），不從座標反查 | 反查要呼叫外部服務（比賽規則、斷網）；個人提供者不顯示地址欄也不送（ADR-030） |

| v2-11 | 頁面不再傳 `title`／`back` 給 T01，標題改由 MR-C60 BrandHeader 顯示 | 設計 v2：App 的標題列與返回鍵網頁不要畫；避免兩個 h1 |
